## Description

`scripts/test-upgrade-cycle.sh` (added in v1.0.10) has several bugs that prevent it from working and — more seriously — caused the fork's real working tree to become dirty with test-scenario fixtures (`docs/PRODUCT-DEFINITION.md`, `app/components/Button.tsx`, modifications to `.agile-flow-overrides`, `.agile-flow-meta/version` reset to `v0.9.0`, etc.). A user running this script after `/upgrade` will see scenario test fixtures appear in their real repo.

Running the script the user-facing way (`bash scripts/test-upgrade-cycle.sh`) on a clean fork at v1.0.10 exits non-zero after the first two test cases and leaves the host repo dirty.

## Bugs found

### 1. False-positive conflict-marker check (script self-matches)

`check_no_conflict_markers` (line 169) greps for the literal string `<<<<<<< ` in `*.md` and `*.sh` files inside the test fork. The script itself is copied into the fork via rsync and contains that exact 7-angle-bracket pattern in its grep command, so the check always fails on a successful upgrade.

```bash
if grep -rq "<<<<<<< " "$test_dir" --include="*.md" --include="*.sh" 2>/dev/null; then
  return 1
fi
```

### 2. Hardcoded expected post-upgrade version

`check_version_updated` (line 177) hardcodes `v1.0.9` as the expected post-upgrade version:

```bash
local expected_version="${2:-v1.0.9}"
```

Upstream is now v1.0.10, so the `version-updated` validator fails even when the upgrade actually succeeded. This will rot on every release.

### 3. Broken cwd between test cases

`run_test_case` does `cd "$test_dir"` (line 236), runs the test, then `rm -rf "$test_dir"` (line 305) — without `cd`ing out first. The parent shell's cwd is now a deleted directory. The next test's `init_test_fork` invokes `rsync` from that invalid cwd, and the rsync receiver dies with `getcwd(): No such file or directory`.

### 4. `init_test_fork` stdout pollution corrupts `$test_dir`

`init_test_fork` is called via command substitution `test_dir=$(init_test_fork "$test_name")` and is supposed to print only the path. But after bug #3 corrupts cwd, the `git commit -q -m "Initial fork state"` (line 57) emits "On branch main / Initial commit / nothing to commit..." to stdout because the test fork ended up empty. That output is captured along with the path, so `cd "$test_dir"` then fails with a multi-line "No such file or directory" error.

### 5. Host working tree gets polluted with scenario fixtures

Most importantly, after running the script the host repo's working tree ends up dirty with content that matches scenarios defined in `test-upgrade-cycle.sh` and `test-dirty-fork.sh` — including `docs/PRODUCT-DEFINITION.md`, `docs/PRODUCT-ROADMAP.md` (overwritten), `app/components/Button.tsx`, `.agile-flow-meta/version` reset to `v0.9.0`, `.agile-flow-overrides`, `.claude/agents/github-ticket-worker.md`, and `docs/ARCHITECTURE.md` / `docs/API.md` (the latter two come from `test-dirty-fork.sh` content, which was never explicitly invoked — suggesting a path/cwd leak between the two test scripts).

This is the most dangerous behaviour: if a user has uncommitted work, running the test helper after `/upgrade` could mix scenario fixtures into their real changes.

### 6. `scripts/report-issue.sh` rejects the upstream value `/upgrade` writes

`/upgrade` records `"upstream": "vibeacademy/agile-flow"` (bare slug) in `.agile-flow-version`, but `scripts/report-issue.sh:148-155` expects a full GitHub URL and exits with:

```
ERROR: Cannot parse GitHub repo from: vibeacademy/agile-flow
Expected format: https://github.com/org/repo
```

So `/report-issue` is unusable out-of-the-box on any fork created by `/upgrade`. Either the producer (`scripts/template-sync.sh` / `/upgrade`) should write the full URL, or the consumer (`report-issue.sh`) should accept the bare-slug format. (This issue was filed via `gh` directly as a workaround.)

## Steps to Reproduce

1. Start from a clean fork at v1.0.9 (or any version before v1.0.10).
2. Run `/upgrade` to sync to v1.0.10 (this adds `scripts/test-upgrade-cycle.sh` and `scripts/test-dirty-fork.sh`).
3. Run `bash scripts/test-upgrade-cycle.sh`.
4. Observe the script exits non-zero after two test cases. Then run `git status` on the host repo.

## Expected Behaviour

- All 7 test scenarios run to completion in isolated temp directories.
- The host repo's working tree is never touched.
- Validators reflect the actual upstream latest version, not a hardcoded `v1.0.9`.
- Conflict-marker detection does not match the script's own search pattern.
- `/report-issue` works on freshly-upgraded forks without manual intervention.

## Suggested Fixes

- Change the conflict-marker grep to use a regex that does not match itself, e.g. `grep -rE '^<{7} '` or exclude the script directory.
- Read the expected version from `.agile-flow-version` (or compute it from the latest GitHub release) instead of hardcoding.
- In `run_test_case` and `run_test_case_compound`, `cd "$REPO_ROOT"` (or `popd`) before `rm -rf "$test_dir"` so the parent shell's cwd stays valid.
- Suppress `git commit` stdout in `init_test_fork` (`>/dev/null 2>&1`) or write the test_dir path to stdout first and route everything else to stderr, so `$()` capture can't be polluted.
- Investigate the host-repo pollution root cause. The most likely culprit is that `apply_scenario` writes to relative paths like `docs/PRODUCT-DEFINITION.md` and depends entirely on a prior `cd "$test_dir"` — if the cd silently failed (e.g. captured-stdout corruption) the writes land in the host repo. Add an explicit `pwd` assertion against `$test_dir` at the top of `apply_scenario` and `run_upgrade`.
- Align the `upstream` field format between `/upgrade` (writes bare slug) and `scripts/report-issue.sh` (expects full URL).
